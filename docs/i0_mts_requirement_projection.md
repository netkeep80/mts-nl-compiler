# I0 — read-only проекция нормативных требований МТС v0.15

Статус: RESEARCH / NO SEMANTIC AUTHORITY. Исследовательская задача:
[issue #91](https://github.com/netkeep80/mts-nl-compiler/issues/91).

## Нормативные входы

Источник — netkeep80/anum_docs на неизменяемом commit
49458b680e0fde9dfbd5861e75e95c9e59bea74a.

- requirements/mts-v0.15.json, Git blob SHA1: f7729caa54f91e1a8632a094667c68e9ee330ec4
- traceability/mts-v0.15.json, Git blob SHA1: 6b43a9c8b6186ff002218b44ef69a57b24460974

Никаких ссылок на плавающий main. При загрузке проверяются точные байты через
Git blob SHA. В отчёте независимо вычисляются SHA-256 обоих исходных файлов
и нормативного текста каждого требования.

Индивидуальный state требования, статус релиза accepted и авторское решение
различаются. Эксперимент не создаёт новых решений Автора и не превращает
предложенные русскоязычные reader-wave тексты в нормативные требования.

## Воспроизведение

Требуется Node.js 24+.

    node scripts/i0_mts_requirement_projection.mjs --github > /tmp/i0-report.json

Альтернатива — локальный read-only checkout anum_docs строго на указанном SHA:

    node scripts/i0_mts_requirement_projection.mjs --anum-dir /path/to/anum_docs

При отсутствии входа, ошибке UTF-8, несоответствии Git-коммита или хеша
команда завершается с ненулевым кодом и не публикует успешный отчёт.
GitHub write permissions не используются. CLI пишет только в stdout/stderr.

    npm test

В наборе тестов используются настоящие закреплённые GitHub-источники;
мутации выполняются только в памяти. CI необходим сетевой доступ к
неизменяемым raw-источникам. Сетевая ошибка означает fail-closed, не SKIP/PASS.

## Выборка и состав проекции

V15-ONTO-01, V15-ONTO-02, V15-NAME-01, V15-JSON-02, V15-FRESH-01.

Это строго **5 выбранных источников отношений из 48** нормативных требований
в закреплённом реестре. Полная валидация соответствия ID между registry и
traceability не расширяет область выборки проекции до 48 требований.

Детерминированный JSON-отчёт содержит:

- точные Git-коммит, пути, Git blob SHA-1 и SHA-256 входов;
- ID, нормативный текст и SHA-256 его декодированных UTF-8 байтов;
- отдельные поля для индивидуального state, принятого релиза и решения Автора;
- JSON Pointer для исходных записей, полей и traceability;
- точные UTF-8 byte offsets JSON-токена строки, включая кавычки;
- исходные ownerIssue, dependsOn, requiredExecutableGates, evidenceRefs;
- вычисленные прямой и **выборочный** обратный индексы: только отношения,
  исходящие от 5 выбранных требований;
- машиночитаемое reverseScope: selectedSourceCount=5,
  registryRequirementCount=48, unindexedSourceCount=43,
  completeAcrossRegistry=false,
  emptyOrMissingEntryMeans=UNKNOWN_OUTSIDE_SELECTION;
- manifest зависимостей и SHA-256 всей проекции.

Позиции в сыром JSON (включая escape-последовательности) не тождественны
позициям в декодированном тексте. Имена relations источника не переименовываются
в requires/implements/verifies repo-guard. Физические идентификаторы Links не
используются. Кандидаты интерпретации вообще не являются входом проекции.

### Граница обратной трассировки

Обратный индекс группирует связи только от выбранных требований, но целевые
ID могут находиться и за пределами выборки. **Пустая/отсутствующая запись НЕ
означает, что зависимых требований в полном реестре нет.** Даже непустая
запись не претендует на перечисление всех зависимых требований среди 48.

Контрпример из закреплённого реестра: от V15-FRESH-01 зависят
V15-FRESH-02 и V15-FRESH-03, но они не выбраны и потому не присутствуют в
reverse.dependsOn[V15-FRESH-01]. От V15-ONTO-01, помимо выбранного
V15-ONTO-02, зависят также невыбранные V15-ONTO-03 и V15-CLOSE-01.
Это специально проверяется отрицательным тестом на реальных источниках.

Для заключений о полном отсутствии зависимостей нужен отдельный обход
всех 48 требований, **который I0 не выполняет**.

## Freshness и отрицательные проверки

assessI0Freshness(manifest, observed) возвращает CURRENT лишь при наличии
обоих необходимых источников с совпадающими хешами. Мутация входа даёт STALE;
отсутствие входа или некорректный/неполный manifest — UNKNOWN.
Изменения файлов вне этих **двух входов** не влияют на узкую проверку.

**CURRENT подтверждает только freshness байтов двух закреплённых JSON.**
Dependency manifest I0 не содержит SHA файлов, упомянутых в evidenceRefs
и requiredExecutableGates; не проверяет их существование или актуальность;
не содержит исходных артефактов, коммитов и свидетельств из других репозиториев.
Следовательно, CURRENT **не доказывает полный межрепозиторный dependency
closure**, корректность доказательств или полноту всей сети требований.

Тестируются: изменение текста и traceability, посторонний файл, отсутствие
входа или requirement ID, дублирование ID и JSON-ключей, противоречие состояний,
подмена accepted на proposed, повреждённые UTF-8/JSON, candidate с попыткой
присвоить ACCEPTED, повторное исполнение и точность исходного byte span.

Изменённые входы сначала могут получить диагностическую ошибку структуры,
но ни при каких обстоятельствах не проходят неизменяемый hash gate.

## Сравнение с repo-guard

В netkeep80/repo-guard уже реализованы типизированные отношения требований,
provenance, BASE→HEAD transitions, content-identity freshness и overlap
implementation/verification. I0 не копирует их и не изменяет repo-guard.

Новая функциональность I0 — только адаптация реальной структуры реестра
anum_docs v0.15 и вычисляемая read-only проекция зависимостей с pinned inputs.
Наличие verification reference не доказывает смысловую корректность
формализации или предметного утверждения.

Межрепозиторные governance-переходы, FORMAL/Γ interoperability, семантическая
эквивалентность, доказательность формализации и научная приёмка — NOT VERIFIED.
