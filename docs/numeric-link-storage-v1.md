# Исследовательская вертикаль числового хранилища Link (v1)

**Авторское решение:** [#51](https://github.com/netkeep80/mts-nl-compiler/issues/51), 2026-10-12.

Вместо текстовых и хеш-производных физических Link ID используется единственный целочисленный \`INTEGER PRIMARY KEY AUTOINCREMENT\` (signed 64-bit). Полюса \`from_id\` и \`to_id\` имеют **отдельные** индексы. Индекс по паре не уникален: две связи с одинаковыми полюсами могут иметь независимые identity. Строковые source-key обозначения при импорте — **временные ссылки во входном файле, не физические ID**, никогда не сохраняются в \`links\` и не вычисляются из полюсов.

## Граница первой реализации

Пока действует исходный canonical \`db/schema.sql\`, эта вертикаль **не заменяет его**: \`src/numeric-link-store-v1.mjs\` содержит целевую схему в константе \`NUMERIC_LINK_SCHEMA_V1\` для независимой исполняемой проверки. Единственная **предметная** таблица — \`links\`. SQLite автоматически ведёт служебную \`sqlite_sequence\` из-за AUTOINCREMENT; это НЕ второе хранилище асети. Проверка физического SQLite-миграционного cutover требует отдельного governance-разрешения на \`db/schema.sql\`.

Схема сохраняет \`string\`, \`weight\`, \`from_uses\`, \`to_uses\`, ограничения на форму атома/пары и валидность веса. Поля \`from_id\`/\`to_id\` имеют отложенные self-referencing FK для циклических/взаимных Link. Транзакционный импорт детерминированно сортирует **внешние импортные ключи**, сначала выделяет ID через SQLite, затем заполняет полюса, пересчитывает производные счётчики, проверяет closure/integrity и публикует транзакцию целиком. Отказ на поздней фазе делает ROLLBACK. Внешние ключи не являются частью постоянной идентичности; при интеграции разных баз нужен протокол разрешения коллизий numeric ID.

## 64 бита и эксплуатационные ограничения

В Node идентификаторы читаются \`setReadBigInts(true)\` и переносятся как \`bigint\`. Для форматов JSON выделенный ID должен быть передан **канонической десятичной строкой**; \`Number\` недопустим после \`2^53-1\`. Не путать десятичную запись идентификатора с хешированием: никакие SHA-256 не участвуют в идентичности Link.

\`AUTOINCREMENT\` гарантирует, что новое автоматически выделенное значение больше прежде подтверждённых ID; это не гарантия отсутствия пропусков и **не запрет переиспользования значения после ROLLBACK**, поскольку отменённые транзакции не были опубликованы. При достижении \`9223372036854775807\` новые автоматические вставки обязаны FAIL/CLOSED. Есть накладные расходы на \`sqlite_sequence\` и запись; сравнить с \`INTEGER PRIMARY KEY\` без AUTOINCREMENT на реальном корпусе как performance-only эксперименте, не меняя решение автора.

## Gate физической миграции

1. Перенести \`src/store.mjs\` и единственный canonical \`db/schema.sql\` с exact governance grant; старые SQLite snapshot/архивы несовместимы без explicit importer.
2. E0–E7 и corpus-эксперименты перестать сохранять \`a:/p:\` SHA как **physical Link ID**. Исследовательский hash-consing может оставаться аналитической структурной метрикой, но не идентификатором физического Link; саму hash-consing метрику придётся пересчитать заново.
3. JSON/FORMAL/Γ адаптеры: различать непрозрачные метатеоретические Link identities, числовую физическую адресацию и внешние временные ссылки. Проверить циклы, параллельные Link, nullable weights, признанные отличия native test-side Γ от production.
4. Утвердить новую версию snapshot/SQL/manifest и deterministic new-ID allocation order; проверить replay SQLite, expiry/gc и Link counts на всех 6 pinned источниках, включая cross-DB rewrite.
5. Не считать этот эксперимент полной нормативной миграцией: canonical main остаётся прежним, пока новая схема не прошла регрессию и независимую авторизацию.

Верификаторы: \`tests/numeric-link-store-v1.test.mjs\` — отдельные sqlite индексы и планы \`EXPLAIN QUERY PLAN\`, BigInt boundary, детерминированный import, parallel/cyclic links, ранний fail, поздний ROLLBACK, delete-no-reuse, exact signed maximum, nested transaction запрет.
