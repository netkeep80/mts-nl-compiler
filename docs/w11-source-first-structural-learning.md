# W11 — исходная частотность до построения Link, затем выбор структуры

Исследовательский этап, без изменения требований, нормативной схемы SQLite, `weight`, и `main`.

## Проверяемая гипотеза

Слепая сбалансированная бинаризация кодирует лишь ~42,47% всех исходных биграмм как цельные Link, и ~6,75% пятёрок. Поэтому `pairCounts` построенного дерева нельзя использовать как объективную частоту исходных подстрок. Предлагаемый W11 отделяет **неизменные статистики исходных символов и перекрывающихся 2–6-грамм** от **обучаемых границ Link**.

## Три экспериментальные ветви

1. **Balanced**: неизменный исходный символ-по-символу binary DAG.
2. **Raw-n-gram chunks**: кандидаты из всех перекрывающихся исходных 2–6-грамм. По частоте выбираем до 256 кандидатов, затем DP максимизирует локально число схлопнутых позиций. Это намеренно простая абляция: она может портить другие полезные повторяющиеся поддеревья.
3. **Learned scalar boundary**: считаем распределение левых/правых соседей *каждого наблюдаемого Unicode-скаляра*, ранжируем кандидатов по `log2(1+freq)*min(H_left,H_right)`, затем **по 48 train** считаем реальное число уникальных пар Link для каждого из 12 предложенных кандидатов и сравниваем с исходным balanced. Если выигрыш есть — запоминаем единственный выбранный скаляр и на **неизменённой модели** строим 12 heldout. Чанк заканчивается непосредственно после выбранного символа; ни пробелы, ни пунктуация не выделены специальным условием. **Число физических Link — не полный MDL.**
4. **Dynamic pair grammar (контроль)**: первый проход считает *все* исходные смежные пары до кодирования; последующие проходы подсчитывают пары оставшихся единиц, строя повторно используемые Link. Не делать вывод о победе, если физическое число Link не уменьшилось.

Для каждого физического сравнения используется принятый однотабличный SQLite Link store, реальные 64-битные ID, те же правила интернирования точных атомов и пар, полное холодное побайтовое восстановление, `VACUUM` bytes. Дополнительная независимая in-memory реализация сверяет точное число физических Link с реальной базой.

**Важно:** кандидат выбора границ проверяется по *полной физической стоимости train-графа*, а не по частоте одиночного символа. Он не является предзаданным распознавателем слов. Замена символа на произвольный скаляр при неизменной статистике не должна менять решение. Дешёвые токены, которых нет в heldout, можно материализовывать как обычные точные атомы.

## Как воспроизвести на GitHub artifact

Из W10 action [проверенная 60-book SQLite + JSON](https://github.com/netkeep80/mts-nl-compiler/actions/runs/38253156259) получить локально `knowledge-large.sqlite` и `large-corpus-performance.json`, затем в checkout с Node 24:

```sh
node scripts/run-source-first-v0.mjs /path/knowledge-large.sqlite /path/large-corpus-performance.json reports/w11-source-first-ab.json
```

Скрипт восстанавливает только первые 8192 Unicode-символа каждого из 60 корней и **не выводит исходные книги**, сохраняет только числовые результаты. 48 из 60 книг по правилу `index % 5 != 4` — train, остальные 12 — heldout. Истинные границы слов, языковая разметка и регулярные выражения **не используются для обучения**. Изменение sample-prefix на полные исходники требует отдельного контролируемого прогона.

## Первое воспроизводимое свидетельство

На 60 × 8192 точных Unicode-символах SQLite W10 (всего 491 520) in-memory pilot до SQL: balanced 152 326 уникальных Link; слепое выделение 256 частых подстрок 164 734 (хуже!); выбранная на train граница — U+0020, с ней 135 683 (−10,93%). Это исследовательские числа из Python-реконструкции опубликованных SQLite-корней и JS-проверки; **до нового SQL-прогона не приравнивать их к измеренным SQLite/VACUUM результатам**. Кандидатный список и затраты на оценивание надо будет расширять независимо, без знания слов.

Предполагаемые следующие исследования: составные/позиционные границы, локальная Δ-алгебра с атомарным cutover корней, MDL с полной стоимостью модели, слоты и классы контекстной заменимости. Никаких претензий на открытие семантики или универсального сжатия из этого опыта.

## W12: контролируемое сравнение разных способов построения Link (12 октября 2026)

Режим: исследовательский, без изменения принятой MTS v0.15, SQLite-схемы и без нормализации исходных текстов. Источник: те же точные 60 книг, восстановленные из [проверенной W10 SQLite](https://github.com/netkeep80/mts-nl-compiler/actions/runs/38253156259); первые 8192 или 16384 Unicode scalars на книгу. Фиксированный split: 48 train (index % 5 != 4), 12 heldout. Каждый метод проверен независимым Unicode replay; обучение контекстного кандидата и всех частот **строго только на 48 train**. При оценке heldout модель не изменяется, но физическое объединение Link допускает интернирование в ранее созданный общий граф.

### Эксперимент A: обучение мест группировки (8192 × 60)

| Стратегия (словаря и границ слов нет) | Уникальных физических Link по всему sample | Вклад отложенных 12 книг в уже обученный физический граф |
|---|---:|---:|
| Нет границ, balanced | 152 326 | 27 489 |
| Лучшая граница **перед** символом | 140 859 | 25 277 |
| Лучшая граница **после** символа | **135 683** | 24 525 |
| После самого частотного символа | 135 683 | 24 525 |
| После лидера контекстной энтропии | 135 683 | 24 525 |
| Жадный поиск до двух «после» | 135 683 | 24 525 |
| Жадный поиск до двух «до/после» | 135 683 | 24 525 |

В этой выборке **все** стратегии, которые могут самостоятельно выбрать одну границу «после», совпали на U+0020; дополнительную границу оптимизатор не принял. Отсюда **нельзя заключать**, что контекст всегда излишен или что слова предопределены. Это конкретная отрицательная абляция.

### Эксперимент B: форма дерева внутри ранее обнаруженных частей

Кандидат `frequencies` вычисляет полные перекрывающиеся *сырьевые* подстроки train длины 2–8 (не использование уже построенных Link). Для очередного фрагмента он рассматривает все разрезы **только внутри него**. Локальный балл одного разреза:

```
score(k) = log2(1 + f(raw[left])) * len(left)^p
         + log2(1 + f(raw[right])) * len(right)^p
         - 0.1 * abs(len(left)-len(right))
```

При длине подстроки > 8 или длине 1 её вклад равен 0. Варианты p=0, 0.5, 1, 2 проверены **на одинаковой выборке и 48 train**. Лучший из заранее заявленного малого набора p=2, обозначен `frequencyQuadratic`. Это **жадный рекурсивный разрез**, не математически точное interval-DP и не глобальный минимум грамматики. Содержимое любой найденной группы точно раскрывается через обычные бинарные Link.

| Метод | 8192 × 60: Link | 16384 × 60: Link |
|---|---:|---:|
| Balanced *без выученной границы* | 152 326 | 278 382 |
| Частотная форма p=2 *без границы* | 145 195 | 261 148 |
| Balanced внутри выученных фрагментов | 135 683 | 244 596 |
| Частотная форма p=1 + выученная граница | 131 769 | 237 449 |
| **Частотная форма p=2 + выученная граница** | **128 633** | **233 229** |
| p=0 + выученная граница | 152 653 | 273 812 |

Итого в главном A/B: **−15,55% / −16,22%** уникальных Link против balanced без границ. Видно, что наличие частоты само по себе не гарантирует выигрыш: p=0 на 8192 хуже, чем частотно-наивная граница, а простые left/right comb могут быть значительно хуже. Подбор p по train — часть стоимости поиска гипотез; нельзя объявлять оптимизацию по heldout.

### Отложенные книги и статистическая устойчивость

Для 16 384 символов: у p=2, относительно balanced с той же выученной границей, **12/12** отложенных фрагментов потребовали меньше Link при **отдельном, независимо инициализированном графе для каждого документа**. Разности числа Link по 12 документам: `[601,518,554,435,476,409,551,516,436,446,453,476]`; средняя экономия **489,25 Link/книгу**. Детерминированная парная бутстрэп-перестановка документов (10 000 повторов, seed=20261012) даёт интервал **[458,58; 520,92] Link/книгу** (перцентильная 95% bootstrap CI). Это описательная статистика для фиксированного корпуса, а не доверительный интервал по всем языкам/книгам. На 8192 средняя экономия 260,08 [249,33;270,42].

После последовательного добавления 12 heldout к уже созданному 48-train графу их совокупная новая цена для 16 384 уменьшается с **44 345** Link (balanced внутри границ) до **42 886** Link (p=2); для 8192 — с 24 525 до 23 704. Это отдельная метрика, она **не равна** сумме независимых одиночных баз каждого heldout-документа.

### Корректность и оставшиеся gates

- Отрицательные и альтернативные методы сохранять. Не называть Link count полным MDL в битах.
- Критерии оценивать по числу **уникальных физических** и **достижимых** Link, `VACUUM`-байтам, фактическому времени, потреблению памяти, 48-train/12-heldout и полному byte-exact replay.
- Новый `SourceFirstShapeNumericLoader` обязан подтвердить `inMemory.physicalLinks == SQLite.links` после rebuild реальных `from_uses/to_uses`, `foreign_key_check` и `integrity_check`, а затем cold-read-only byte-exact replay.
- Запуск дополнительных методов на точных pinned данных, уже извлечённых из физической W10-базы: `W12_METHOD_GRID=1 W11_SCALARS_PER_BOOK=16384 node scripts/run-source-first-v0.mjs knowledge-large.sqlite large-corpus-performance.json /tmp/W12-results.json`. Исходники книг не включать в артефакты.
- Обобщение на **полные 11 017 443 Unicode scalars** остаётся незавершённым; модель пока не выделяет морфемные классы, слоты или смысловые отношения. Направление от source-first статистики к классовой модели W9 нужно проверять отдельно.


### W12 физическая SQLite: независимая проверка целостности

Таблицы выше, выведенные из in-memory модели, **не** принимались на веру. Отдельный Python-верификатор строит `links` с тем же точным SQL DDL W10, без физических content-hash IDs, с `AUTOINCREMENT`, точным интернированием полюсных пар и исходными префиксами того же корпуса. Он пересчитывает `from_uses/to_uses`, требует пустой `PRAGMA foreign_key_check`, `PRAGMA integrity_check = ok`, запускает `VACUUM`, после чего открывает физическую SQLite **read-only**, заново обходит все 60 корней и сравнивает байты каждого восстановленного документа. Все числовые ID выделены независимо от in-memory модели. Количество физических строк точно совпало с независимой моделью; конкретный размер VACUUM зависит от порядка выделения SQLite ID и порядка вставки.

| Режим | 8192 × 60 Link | 8192 VACUUM bytes | 16384 × 60 Link | 16384 VACUUM bytes |
|---|---:|---:|---:|---:|
| Без границ, balanced | 152 326 | 6 361 088 | 278 382 | 11 771 904 |
| Без границ, частотная форма p=2 | 145 195 | 6 041 600 | 261 148 | 11 018 240 |
| После обученного скаляра, balanced | 135 683 | 5 632 000 | 244 596 | 10 293 248 |
| **Скалярная граница + частотная форма p=2** | **128 633** | **5 324 800** | **233 229** | **9 789 440** |

Экономия совместного метода: **−15,55% Link / −16,29% VACUUM** для 8192 и **−16,22% Link / −16,84% VACUUM** для 16384 относительно полной независимой balanced сборки. Холодный побайтовый replay: **60/60 PASS** в каждой строке. Нет доказательства аналогичного процента на всех 11 млн символов, и никакого утверждения о семантической точности не делается.

Оптимизация вычислений: при сравнении всех разрезов субфрагмента длины больше 16 значение обученного сырьевого частотного бонуса ненулевое только для детей длины 2–8; остальные разрезы имеют исключительно балансовый штраф и потому лучший из них — центральный. Поэтому для длинных фрагментов можно точно эквивалентно проверять первые 8, последние 8 и оба центральных разреза. Это ускорение не меняет балл или выбранную топологию и проверяется тестом.
