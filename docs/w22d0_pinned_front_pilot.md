# W22-D0 — фиксированный 48/12 пилот формы дуплетов на 60 книгах

**Эксперимент, не научная приёмка общего компрессора.** Включается в уже принятый pipeline \`scripts/build-large-corpus.mjs\`, **без изменений protected workflow**. Исходники ровно 60 русскоязычных произведений из \`d0rj/RusLit\` @ \`4509680428729da225a73a22008133660f92bb7e\`, отдельный \`corpus/large-books-v1.json\` фиксирует пути, Git blob SHA и точные байтовые размеры. Исходные книги не коммитятся и никогда не сериализуются в дополнительный отчёт.

## Сплит и точная граница данных

Как в существующем W4, **нулевой индекс % 5 == 4** определяет 12 heldout книг, оставшиеся 48 — train. W22-D0 намеренно маленький *пилот*: для выбора формы группировки используются только **первые четыре обучающие книги**, из каждой первые 32 точных Unicode-скаляра; для контроля к каждому из этих четырёх входов присоединяется 32-скалярный фрагмент другой фиксированной **обучающей** книги.

Для окна шириной **6** (42 бинарных дерева) и **8** (429 деревьев) с фиксированным **началом 8** перечисляются *все* бинаризации этих фрагментов. Для каждой из 4 обучающих пар создаётся отдельная независимая SQLite-база с реальными числовыми \`AUTOINCREMENT\` Link IDs. Суммируется число уникальных физических Link **пар**. Выбирается один порядковый номер **формы дерева** (Catalan ordinal), минимизирующий сумму на train; равенство решается по порядковому номеру. Таким образом, **не** обучается словарь естественного языка, не обучается маска пробелов, не выбирается оптимальное смещение на heldout и не переносится физический номер Link.

После заморозки \`selectedOrdinal\` берутся **все 12 heldout книги**. Для каждого heldout источника первые 32 скаляра группируются в том же окне/смещении, но **без перебора вариантов для принятия решения**: оцениваются только три заранее фиксированные формы — \`balanced\`, \`left\` и \`train-selected\`. Контекстное соседнее дерево берётся из **первой обучающей книги** и неизменно для всех проверочных случаев. Форма остальных 24 символов целевого фрагмента сбалансирована и присоединяется тем же способом во всех трёх сравнениях.

## Реальная измеримая величина

Для каждого сочетания \`(heldout book, width, mode)\` строится **новая независимая SQLite** (одна и та же физическая схема \`db/schema.sql\`), с явным интернированием идентичных атомов и полюсных пар. Оба полных 32-символьных текстовых фрагмента побайтово восстанавливаются из физического Link через \`replayNumericRoots\`, затем проходит \`VACUUM INTO\`, и из **холодной read-only SQLite** они восстанавливаются повторно.

- \`physicalPairs\`, \`physicalLinks\`: число действительно сохранённых SQLite Link строк, без мнимых локальных hash-ID.
- \`sqliteVacuumBytes\`: суммарный физический размер базы **для сравнимого маленького двухдокументного случая**. Размер отдельной такой БД может оставаться одинаковым из-за округления страниц; нулевое байтовое изменение не опровергает отличия количества Link.
- \`reusedPairInsertions\`: явно выполненное переиспользование созданных пар (не физический \`from_uses/to_uses\` и не число occurrences в исходных книгах).
- \`deltaLinksVsBalanced\`, \`deltaPairsVsBalanced\`, \`deltaBytesVsBalanced\`: **train-selected минус balanced**; отрицательные значения — экономия на heldout, положительные — регресс, нулевые — равенство.
- \`heldoutImprovedDocs\`, \`heldoutRegressedDocs\`, \`heldoutTiedDocs\`: количество отложенных книг с соответствующим знаком отличия *реальных сохранённых Link*. Все невыгодные исходы публикуются.

Тайминги \`tuningWallMs\` и \`heldoutWallMs\` относятся к действительному Node/SQLite исполнению **этих ограниченных срезов**, но не экстраполируются на 20 МБ книг. В отчёте сохраняются **SHA-256 источника и фрагмента**, ID книг, количество скаляров и размер исходных байтов — **не их текст**.

## Воспроизведение / ограничения

При наличии 60 exact-pinned книг выполнить:

\`\`\`bash
node --expose-gc --max-old-space-size=5500 scripts/build-large-corpus.mjs
\`\`\`

CI workflow \`Full 60-book Russian corpus and TOP1000\` уже запускается при изменении \`scripts/build-large-corpus.mjs\`; после успешного полного исходного baseline добавляет \`W22D0_60_BOOK_HELDOUT\`. Полный JSON помещается в \`reports/large-corpus-performance.json.w22D0\`, поэтому он входит в **существующий artifact** без расширения protected workflow.

Обычные Node-тесты с **60 полностью синтетическими контролируемыми документами** проверяют точный 48/12, два размера окна, побайтовый cold replay, регрессы как допустимые результаты и инвариантность выбора формы при изменении **только heldout**. Они сами по себе **не являются** запуском на настоящих 60 книгах. Успешный полный workflow нужен для такого утверждения.

**Научная граница:** W22-D0 не претендует на улучшение компрессии всех 60 книг; проверяются только 32-скалярные фрагменты в положении 8, и оптимизируется **форма дерева**, выбранная на четырёх train-образцах. Старые целые W4/word-aligned/balanced метрики, обученные на 48 книгах, остаются отдельными, **несопоставимыми численно** при данном крошечном окне. Нельзя объявлять доказанное превосходство фронта, семантические вероятности или production-ready асеть из этого пилота. Следующий этап требует валидной функции стоимости всего активного/исторического корпуса и масштабируемого online-алгоритма, а не 429 пересборок SQLite на каждый символ каждой книги.

**Нулевой результат важен:** для ширины 8 никакой измеримой экономии физических Link или SQLite VACUUM байтов на независимых фрагментах не обнаружено. Для ширины 6 обнаружена лишь **одна** связь в совокупности из 12 двухдокументных опытов, без изменения размера SQLite. Поэтому по этому пилоту нельзя обосновать внедрение оптимизации формы дерева как улучшения всего корпуса. Он скорее мотивирует алгоритм, который выбирает новые локальные связи с учётом *физически существующих* Link, стоимости переиспользования, частоты source-occurrences и истории асети; это следующий отдельный исследовательский этап.

**Важная тонкость:** полная исходная база, 60-книжный W4 и W22-D0 имеют *разные объёмы входа/модели*, поэтому в этом документе их числа приведены по отдельности, а не как единый показатель улучшения W22-D0 на 2.7 млн Link. Данные измерений привязаны к указанному commit upstream RusLit и одноразовому CI runner; нестабильные тайминги не обобщаются на Windows/Linux вне проверенной среды.
